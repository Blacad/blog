微服务是一种架构风格，它把一个大的业务系统拆成多个可以独立开发、部署、扩缩容的服务，不同的服务之间通过网络通信。

<!-- more -->

每个微服务系统，都是一个独立完整的系统，而多个微服务系统共同构成完整的业务系统。
由于每个微服务系统都是独立的，因此它们都可以有自己独立的数据库等等，为了保证可用性，往往会需要分布式设计实现 异步、可靠事件传递以及最终一致性等问题。

在架构设计上(核心区别)，微服务系统 vs 单体系统

```text
传统单体系统
┌──────────────────────────┐
│ 用户 / 订单 / 支付 / 搜索   │
│                          │
│    MySQL  Redis  ...     │
└──────────────────────────┘

用户服务 ── MySQL ...
订单服务 ── MySQL ...
支付服务 ── MySQL ...
搜索服务 ── Elasticsearch ...
        \      /
          Kafka
```

在事务管理上，微服务系统 vs 单体系统

```text
单体系统：
全局 ACID 事务

微服务：
本地 ACID
   +
可靠消息
   +
幂等
   +
重试
   +
补偿
   ↓
最终一致性
```

微服务 vs 单体系统

```text
单体
一个主要部署单元
完整业务逻辑主要存在于内部模块协作
模块调用通常是进程内调用

微服务
多个独立部署单元
每个服务拥有明确业务边界
跨服务通过网络通信
服务可以独立开发、部署、扩容
通常尽量拥有自己的数据边界
```


误区：
微服务架构并不是说用了很多独立服务的系统，一个单体系统也可以使用很多服务，***它的核心区别在于 单体系统直接实现完整的业务逻辑，而微服务架构是把原本一个单体应用中的业务能力拆成多个独立部署的小型应用，每个服务负责一个相对完整的业务边界，再通过网络协作完成更大的业务流程***
